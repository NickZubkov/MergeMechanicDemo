# MergeMechanicDemo

Тестовое задание Unity Developer (Team Planet): кор-механика мерджа из Gossip Harbor —
поле 7×9, спавнер предметов, цепочки уровней и UI-кнопка с таймером, выдающая новый спавнер.

**Unity 2022.3.62f3 LTS** · Built-in Render Pipeline · Zenject · UniTask

| | |
|---|---|
| Сцена | `Assets/_Project/Scenes/Game.unity` (единственная, индекс 0 в Build Settings) |
| Код | `Assets/_Project/Scripts/`, namespace `MergeMechanic`, ~800 строк |
| Конфиги | `Assets/_Project/Configs/` — правила задаются данными, а не кодом |
| WebGL-сборка | меню `MergeMechanic → Build WebGL`; результат в `Builds/WebGL`, в репозиторий не попадает |

Управление: **тап** по спавнеру выдаёт предмет, **перетаскивание** предмета на такой же —
мердж. Кнопка снизу запускает таймер, по истечении которого на поле появляется спавнер.

Ниже — ответ на **Задание 2**: как проект устроен внутри, какие решения приняты и почему.

---

## 1. Какая часть кода за что отвечает

Четыре слоя, зависимости идут строго в одну сторону: **конфиги → домен → сервисы → представление**.

### Configs — данные для гейм-дизайнера

Пять ScriptableObject-типов и три `[Serializable]`-класса внутри них. Корневой — `GameConfig`,
единственная ссылка в инсталлере, остальное подтягивается через него.

| Тип | Что задаёт |
|---|---|
| `GameConfig` | ссылки на `BoardConfig` и `SpawnerTimerConfig` |
| `BoardConfig` | размеры поля (7×9) и стартовую раскладку списком «цепочка + уровень + клетка» |
| `MergeChainConfig` | цепочку уровней; `MaxLevel` = длина списка, потолок мерджа берётся отсюда |
| `ChainLevel` | подпись, цвет, спрайт и таблицу спавна одного уровня |
| `SpawnTable` / `SpawnEntry` | что и с каким весом спавнится |
| `SpawnerTimerConfig` | длительность отсчёта и что таймер выдаёт |

Проверки данных живут в `OnValidate`: позиция вне поля, две вещи в одной клетке, ссылка на
несуществующий уровень цепочки — всё это ошибкой падает в консоль при редактировании ассета,
а не в рантайме.

### Domain — правила игры

- `Board` — сетка клеток: разместить, убрать, переместить, найти случайную свободную. Держит
  счётчик занятых клеток, поэтому «есть ли место» — константа по времени. Нарушение инварианта
  (запись в занятую клетку, выход за поле) бросает исключение сразу, а не портит состояние молча.
- `BoardObject` — объект на поле: id, цепочка, уровень, позиция. `IsMaxLevel` и `CanSpawn`
  вычисляются из конфига цепочки, а не хранятся флагами.
- `MergeRule` — одно чистое условие: та же цепочка, тот же уровень, не потолок.
- `WeightedPicker` + `IRandomProvider` — выбор по весам. Случайность за интерфейсом, поэтому
  раздачу предметов можно сделать детерминированной, не трогая правила.

### Services — состояние

- `GameBoardService` (`IGameBoard`) — **единственное место, где меняется поле**. Вся работа
  входит через один метод `TryInteract(from, to)`, который возвращает `InteractionResult`
  (`Spawned` / `Moved` / `Merged` / `Rejected`) и публикует сигнал о случившемся.
- `SpawnerTimerService` (`ISpawnerTimer`) — обратный отсчёт на UniTask. По истечении, если
  места нет, уходит в состояние `WaitingForSpace` и ставит спавнер, как только клетка
  освободится: таймер не сгорает впустую. Отмена — честная, через `CancellationTokenSource`
  в `Dispose`.

### Signals — три события

`BoardObjectSpawned`, `BoardObjectMoved`, `BoardObjectsMerged`. Через них сервис сообщает
о произошедшем, ничего не зная о сцене.

### Presentation — отражение модели

- `BoardView` — геометрия: строит клетки, переводит клетку ↔ мир ↔ экран, подгоняет камеру.
- `BoardObjectView` (+ `Factory`) — спрайт и подпись одного объекта.
- `BoardPresenter` — подписан на три сигнала и создаёт, двигает, удаляет вьюхи. Сцена никогда
  не «решает» — только отражает модель.
- `DragInputController` — перетаскивание на legacy `Input.*`. Правил не знает: собирает жест
  и отдаёт его в `TryInteract`.
- `SpawnerTimerButtonView` — кнопка и надпись таймера.

### Installers / Editor

`GameInstaller` — composition root: биндинги, объявление сигналов, фабрика вьюх.
`BuildScript` — WebGL-сборка пунктом меню и из CLI.

## 2. Какую структуру выбрали и почему

**Спавнер — не отдельная сущность, а уровень цепочки с непустой таблицей спавна.**

Это главное решение, из него следует почти всё остальное. В ТЗ спавнер требуется мерджить
со спавнером, получая спавнер 2 уровня с другими весами. Если бы спавнер был отдельным типом,
пришлось бы дублировать для него мердж, перемещение, потолок цепочки и правило тапа. При
выбранной модели предметы и спавнеры — один и тот же `BoardObject`, отличаются только данными
в конфиге: у уровня спавнера таблица спавна заполнена, у предмета пуста. Спавнер 2 уровня
с весами 50/50 — это две строки в ассете, а не строка кода.

**Одна точка входа для ввода.** `TryInteract(from, to)`: тап — это `from == to`. Отдельного
распознавания тапа нет вообще, а слой ввода не знает ни одного игрового правила. Добавить
новый жест — значит добавить вызов, а не ветку в правилах.

**Состояние меняется только в `GameBoardService`.** Сцена — отражение модели: презентер
подписан на сигналы и не принимает решений. Из-за этого модель можно прогонять без сцены —
чем я и пользовался при проверке, дёргая `TryInteract` прямо через контейнер и сверяя
результат с тем, что видно на сцене.

**Слои разведены по зависимостям, а не по папкам.** Домен не знает про сервисы, сервисы —
про презентер, презентер — про ввод. `UnityEngine` в домене используется только ради
`Vector2Int` и `Mathf`.

**Данных больше, чем кода.** Требование ТЗ «гейм-дизайнер может вносить изменения» закрыто
тем, что в конфиг вынесены не только числа, но и структура: длина цепочки, стартовая раскладка,
таблицы спавна, что выдаёт таймер. Четыре уровня предметов и два уровня спавнеров нигде
не зашиты — код читает `Levels.Count`.

**Без asmdef.** Разрезка оправдана, когда есть тесты и надо изолировать домен от `UnityEngine`.
Тесты вне скоупа, поэтому весь код в `Assembly-CSharp` — иначе это цена без выгоды.

## 3. Какие паттерны использовали

| Паттерн | Где и зачем |
|---|---|
| **Dependency Injection / IoC** | Zenject; `GameInstaller` — composition root, единственное место, где известны конкретные типы |
| **Dependency Inversion** | `IRandomProvider`, `IGameBoard`, `IBoardLayout` — код зависит от интерфейсов, а не от реализаций |
| **Observer / Publish-Subscribe** | `SignalBus` и три сигнала: сервис не знает о существовании презентера |
| **MVP** | модель (домен + сервис) → `BoardPresenter` → пассивные вьюхи; вьюхи не содержат логики |
| **Factory** | `BoardObjectView.Factory` на `PlaceholderFactory` — Zenject инжектит зависимости в созданные из префаба вьюхи |
| **Strategy через данные** | таблица спавна вместо ветвлений: поведение уровня задаётся ассетом, а не кодом |
| **Interface Segregation** | `IBoardLayout` (координаты) и `IBoardBuilder` (построение) разделены, чтобы контроллер ввода не видел метод, разрушающий сцену; `IBoardObjectViews` отдаёт презентеру ровно одну операцию |
| **Result object** | `InteractionResult` вместо исключений: отказ хода — штатная ситуация, а не ошибка |
| **Guard clauses** | инварианты `Board` и `BoardObject` защищены исключениями в точке нарушения |

Сознательно **не** применялись: пул объектов (на 63 клетках `Instantiate`/`Destroy` дешевле
поддержки пула), Service Locator (антипаттерн при живом DI), Update-менеджер (`ITickable`
Zenject достаточно).

## 4. Какие были трудности

**Порядок инициализации в Zenject.** Если бы доска строилась в `IInitializable.Initialize`,
корректность зависела бы от порядка биндингов: презентер мог подписаться после того, как
стартовая раскладка уже разошлась сигналами. Решено тем, что `GameBoardService` строит поле
в конструкторе и намеренно **не** является `IInitializable`, а стартовая раскладка сигналов
не публикует — презентер читает готовое состояние при своей инициализации. Порядок биндингов
перестал что-либо значить.

**Ввод оказался самой дефектной частью.** Два дефекта нашлись только на код-ревью, оба
незаметны при аккуратной проверке руками:

- Ветки в `Tick` были связаны `else if`, а нажатие и отпускание мыши могут прийти **в одном
  кадре** — при быстром тапе или низком FPS в браузере. Тогда выполнялся только захват, тап
  по спавнеру молча пропадал, а перетаскивание оставалось «залипшим»: следующий клик мимо поля
  выполнял ход объектом, которого игрок не трогал.
- Предмет намеренно сохраняет смещение «за какое место взяли», а целевая клетка считалась
  по позиции курсора. Разойтись они могут почти на клетку: предмет визуально лежит на своей
  паре, а мердж не происходит. Исправлено переводом хода на позицию спрайта.

**Мир и UI масштабируются независимо.** Камера подгонялась под поле, а кнопка живёт в экранных
пикселях с `CanvasScaler` — в WebGL-билде она легла на нижний ряд клеток. Причём в редакторе
проблема не воспроизводилась: там было другое разрешение Game View. Решено тем, что камера
резервирует снизу полосу, а её размер берётся из `RectTransform` самой кнопки — так число
остаётся верным при любом разрешении.

## 5. Что бы улучшили

По убыванию пользы:

1. **Юнит-тесты** на `MergeRule`, `WeightedPicker` и `TryInteract` — с разрезкой на asmdef,
   чтобы домен не зависел от `UnityEngine`. Случайность уже за `IRandomProvider`, так что
   тесты писались бы без единого мока. Оба дефекта ввода тестами бы не поймались, а вот
   правила поля покрылись бы полностью.
2. **Визуальный фидбек.** Сейчас отказ хода никак не показан: предмет просто возвращается.
   Не хватает подсветки целевой клетки, плавного возврата и «пульса» при мердже — это делалось бы
   на DOTween. Интерполяция позиции, масштаба и цвета с готовыми easing-кривыми пишется одной
   строкой, а связки вроде «подлетел из спавнера → спружинил» собираются в `Sequence`; писать
   то же самое вручную на корутинах или UniTask-циклах смысла нет. UniTask при этом остаётся
   там, где он уместен, — ожидание и отмена: твин через интеграцию UniTask можно `await`-ить
   и гасить тем же `CancellationToken`, что и остальную асинхронщину.
3. **Корректная обработка касаний** для APK: `EventSystem.IsPointerOverGameObject()` без
   `fingerId` опрашивает мышь, поэтому на телефоне не погасит перетаскивание, начатое
   на кнопке.
4. **Сохранение состояния** поля и идущего таймера между сессиями — сериализация модели
   в JSON и `PlayerPrefs`.
5. **События вместо опроса** в паре мест: кнопка таймера каждый кадр читает состояние,
   а ожидание свободной клетки крутится на `WaitUntil`. При текущих масштабах это ничего
   не стоит, но событийная модель в проекте уже есть — логичнее довести её до конца.
6. **Логирование через абстракцию** вместо прямого `Debug` в слое сервисов — это первое,
   что помешает вынести домен в отдельную сборку.

## 6. AI-инструменты: что делегировали и что пришлось исправлять

### Инструменты

- **Claude Code (Opus)** — основной инструмент, прошёл весь цикл: дизайн-документ → план
  на 14 задач → реализация по задачам → проверка в Play Mode → код-ревью → рефакторинг →
  WebGL-сборка. Работа велась по согласованной письменной спеке, а не по устным просьбам:
  сначала фиксировались решения и границы скоупа, потом писался код.
- **MCP for Unity** — управление редактором из того же чата: создание ассетов, префабов
  и сцены через `SerializedObject` (все поля приватные, руками в инспекторе это дольше),
  вход в Play Mode, чтение консоли, запуск сборки. Механика проверялась прогоном сценариев
  ТЗ прямо через DI-контейнер со сверкой модели и сцены.

### Что делегировалось

Генерация кода по утверждённой архитектуре, рутина в редакторе, а также **второй проход
код-ревью** — отдельным агентом, независимо от основного.
